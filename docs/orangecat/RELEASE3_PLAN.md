# Orange Cat Release 3: one order of work

**Version:** 0.2 (November 1, 2026; the numbers follow FLASH_MAP_R3.md 0.2 after its review; design only; for the owner to read before any flash map or format change goes into code)
**Joins:** FX_MODULES_PLAN.md 0.3 (the effects as modules), MODULE_FORMAT_R3.md 0.2 (fw_pages version 3, the effect descriptor; Session C), PROJECT_FORMAT_R3.md 0.6 (the project format revision; Session C, on ui-build / ui-fix), FLASH_MAP_R3.md 0.1 (the module area), UI_BUILD.md (the interface's budget and hardware checks)

## 1. What Release 3 is

SHAPES leaves the firmware and ships as its module (the owner's decision); the effects that can move become modules (DUB TAPE first, the reverb modes, the FX layer's buffer effects; DIST, CHORUS, AUTO PAN, ROOM, DELAY and the master chain stay); the module area grows so they fit beside SHAPES and WHEEL; the project format revision (phrases owned by the project, scenes, Performance Mode) ships whole; the installer page carries the two one-way doors in plain words. Release 2 (0.16.0) stays on the Nightly channel until the first Release 3 Nightly; Standard stays 0.15.0 until the owner says.

## 2. The numbers that frame it (measured in round 11, b1997d1's build set)

- Image 562,144 B; the body's room 573,440 B (`BODY_MAX`); free 15,104 B. `MELODEE_SHAPES=0` frees **23,528 B** (538,616 B): free 38,632 B.
- Against that: the effect modules' host and registry 2 to 4 KB (FX_MODULES_PLAN.md 6; **the 11 to 14 KB gain quoted there does not include 7a**: 7a is the interface's fw_pages version 3 checker, 1,100 to 1,500 B, counted in UI_BUILD.md's budget, and the two must be added, not netted), the format revision about 11,400 B (PROJECT_FORMAT_R3.md 11.2b), the reserve 8 KB. Sum: 38,632 - (3,000 + 1,500 + 11,400 + 8,192) = **14,540 B** left at the central estimates once the resident DUB (8,500) is still in the image, and **about 23,000 B** once the resident copies of the moved effects are removed (the release after each module ships). It fits; the order below keeps the resident copies only as long as the gate needs them.
- The module area: 12 sectors hold SHAPES 6 and WHEEL 4; the effects set needs 16 (SHAPES 6, WHEEL 4, DUB 3, the reverb modes 1, the FX layer 2, header pages counted), the three engines 18, both 24: FLASH_MAP_R3.md gives 18, so the Prophet stays an alternative to the effects unless WHEEL is re-cut to one sector.
- RAM: the effect modules' instance contexts and the knob records about 330 B + 16 B (MODULE_FORMAT_R3.md 9); the arena rule stands (the owner's: a cost is a problem only if a real mix misses the deadline).

## 3. Answers to Session C's open items (PROJECT_FORMAT_R3.md 12, "for Session A")

- **(b) SHAPES-out on the real build set:** 23,528 B (section 2).
- **(c) Whether the effect modules' 11 to 14 KB includes 7a:** no. The 11 to 14 KB is what steps 1 to 3 and CLOUD of FX_MODULES_PLAN.md free net of that plan's own cost (registry, module-id install path, loader kind handling, host glue, 2 to 4 KB). 7a is a separate 1,100 to 1,500 B and stays in UI_BUILD.md's column. Session C's table (11.2b) is right to keep them separate.
- **(d) Engines keyed by slot number:** confirmed. `ENGINES[]` is indexed by the engine number (engines.c), `eng_register` registers a module under its header's engine number, the module geometry table is keyed by engine (oc_module.c `oc_mod_geo_of(engine)`), and MODULE_FORMAT_R3.md section 3 makes it final: an engine module has no module id. A project's instrument reference resolves by slot number; a slot with nothing registered is "not installed" (8.2). Effect modules are the ones keyed by (module id, version, parameter id).
- **(f) The arena's block model:** two models, both in use today, and the plan keeps both. *Engine states* are taken in exact bytes (`eng_state_prepare` through `resource_get`: MACRO 11,156 B a track, the arena's blocks are 4 B); *the effects' work memory* is in 4 KB segments (`JFX_SEG` 2,048 samples of int16: the shared DELAY's 16 segments, DUB's `DUB_MAXSEG` line blocks, `jfx_take` for the small objects in exact bytes). An effect module declares `ram_state` in bytes and `ram_work_min/max` in 4 KB blocks (FX_MODULES_PLAN.md 4): exact bytes for the state, blocks for the lines. PROJECT_FORMAT_R3.md's own arrays go in `.pool` at exact size (its A7), not in the arena.
- **(g) The module area's sector budget:** FLASH_MAP_R3.md. The 11 to 14 KB assumes SHAPES (6), WHEEL (4), DUB (3), the reverb modes (1) and the FX layer (2) installed at once: 16 sectors, which 18 holds with 2 spare; the Prophet beside them would need 24.
- **(a) and (e)** stay with their owners: whether a shipped set uses SHAPES (the set files: `tools/check_set_test.py`'s inputs; I have not looked, said plainly), and the review and timing of the fade and the staged phrase (Session A reviews them when they are cut, as the knob macros were).

## 4. What the installer page must say

- **For SHAPES, from the first Nightly with `MELODEE_SHAPES=0`:** "This build has no SHAPES inside it. Tick the SHAPES module (it is ticked) or tracks that use SHAPES will be silent and flagged until it is installed; your projects and sounds keep their SHAPES settings." The module and the pack go in the same install (the page already installs firmware, pack and modules in one go; the pack still carries SHAPES' tables).
- **For the Prophet:** "The Prophet and SHAPES both fit only when the module area is the Release 3 one (18 sectors); on an earlier firmware the Prophet takes SHAPES' place." After the flash map ships the line goes.
- **For a unit upgraded from a SHAPES-in build:** nothing is lost: the pack is the same object, projects reference SHAPES by its slot number (14), and the module registers under it. The page says: "Your unit had SHAPES built in; this build loads it as a module. Install the module in this step (ticked)." A unit that skips the module hears silence on SHAPES tracks with a flag on the track, as PROJECT_FORMAT_R3.md 8.2 says; nothing is converted or deleted.
- **For the format revision's one-way door** (PROJECT_FORMAT_R3.md 10): the warning and the backup gate as written there: a full backup first, then the firmware, and no way back for projects saved by the new firmware.
- **For the flash map's downgrade hazard** (FLASH_MAP_R3.md 4B): "A firmware older than this one does not see modules installed in the new part of the module area; going back means installing those modules again."

## 5. The one order of work

Each step is its own branch from linux-hw, with an independent review before its merge and the host suite on CI's switches; nothing is flashed to the unit before both; the Nightly after each merge is installed on the test unit from the live page as the owner will. The doors are marked **[door]**: a step after which something cannot be undone for the units that took it.

Why this order: 1 before everything because nothing else fits without it and it changes no format; 2 as soon as the page's text is ready, because every later step's budget assumes it; 3 before 4 because the effects' pages and knobs ride on version 3 and both rewrite `fw_pages_t`; 4 and 5 before 6 because a module cannot be installed before the host can run one and the installer can name it; 7 after 6 because the revision's budget (11.2b) assumes DUB's resident copy gone and because its one-way door should open once, late, after the module path has been on the Nightly for a while; 8 after 7 because the revision marks the places the plan is revised against (**[format]**) and the smaller effects are the easiest to re-cut. Steps 1 and 2 can share one Nightly; 3 and 4 can share one; nothing else shares.

## 6. What is decided here and what is not

Decided (the safer reading, for the owner to overturn): option B of the flash map with the start numbering kept at 0xC8000 (no published module package changes meaning); 7a counted separately from the effects' 11 to 14 KB; engines stay keyed by slot number; the format revision ships whole and last but one; the resident copy of every moved effect stays one Nightly beside its module. Not decided: the capability words' exact packing (FX_MODULES_PLAN.md 4, Session A when step 5 is cut); whether the Prophet ships in Release 3's set (it fits with 18 sectors; the owner's call); the sample slot's final size (Phase 9); whether the web editor learns `kdef` and scene bytes through a new command (Session D).

**Stop here.** No flash map change goes into code before the owner has read this plan (BUILD.md 7.22, item 5).
