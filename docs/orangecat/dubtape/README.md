# DUB TAPE: the research prototype's documents

These files were written by the DUB TAPE research session (October 26, 2026) and are copied here unchanged. The plan that
uses them is `docs/orangecat/DUB_TAPE_PLAN.md` (revision 0.3). Nothing here is firmware; nothing here has run on the unit.

| File | What it is |
|---|---|
| DESIGN.md | the algorithm: one int16 line, up to four heads at multiples of TIME, one regeneration path (HP, resonant LP, cubic soft clip at the write), the tape-speed wow model, the rate converters |
| EVALUATION.md | the measurements read out: spectral evolution, stability at FEEDBACK 1.2, aliasing, noise, parameter-change splatter, RAM and CPU (instruction counts for the FM-1 build) |
| MEASUREMENTS.md | the raw tables the evaluation reads from (generated by the prototype's tools/measure.c) |
| BENCH_HOST.md | host timings, one and four instances (an x86 proxy, not the unit) |
| PARAMETERS.md | controls, patterns (SINGLE SKANK SLAP TRIPLE GALLOP SPREAD) and the five starting presets |
| SOURCE_SURVEY.md | open-source tape echoes and delay primitives, with licenses; what may and may not be used in a GPL-3.0-only firmware |
| HANDOFF.md | the research session's own handoff |
| RENDERS.csv | the render list: scene, variant, line size, peak |

Two corrections to read them with:

1. HANDOFF.md and EVALUATION.md size the audio arena at 48 KiB and conclude that four instances do not fit. 48 KiB is the linker's floor (`_resource_minimum` in firmware/app.ld), not the arena. The arena is five banks of 125 KB plus 14 KB of cache RAM, plus 36 KB of card pool when the card is idle. DUB_TAPE_PLAN.md section 0a and section 6 have the real figures and the fit table. The per-track requirement stands; the shared-bus instance the handoff recommends is the first integration step (plan section 4.5), not the end state.
2. The listening test (plan section 0b) picked the half-rate line (22.05 kHz) over the quarter rate. The quarter rate is the automatic fallback for long heads, not the default.

## Where the rest of the prototype is

The prototype's source (`src/dubdelay.c`, `src/dubdelay.h`, `src/dd_math.h`), its tools (`tools/measure.c`, `tools/bench.c`,
`tools/render.c`, `tools/envelope.py`), its Makefile (`make all-results`, `make fm1`) and the 45 renders are on the Linux
PC at `/home/userzero/dubtape-research`, a separate local git repository on branch `research/dub-tape`, **not committed and
not on GitHub**. The files carry `SPDX-License-Identifier: GPL-3.0-only` and no copyright line; AGENTS.md's attribution line
goes on any file that is ported. No third-party code was copied (SOURCE_SURVEY.md).

## What Session A does with this branch

In this order, each step its own commit on this branch, nothing merged to sonnet-work, linux-hw or drum-kits:

1. Commit the prototype's source and tools here as `tools/dubtape/` (the source, the tools, the Makefile; not the 45 WAVs,
   which stay on the PC), so the measurements can be regenerated by anyone with the repo. Run `make all-results` and
   `make fm1` once from the committed copy and record both in BUILD.md.
2. Read DUB_TAPE_PLAN.md in full, then answer its section 9 for the user in BUILD.md (the decisions are the user's; the
   measurements are Session A's): the CPU1 cost of one instance on the unit comes first (plan section 8, rows 1 and 2),
   and nothing else in the plan is built until that row exists.
3. Stage 1 (plan section 4.5): the kernel as a DUB model of the shared DELAY, on the delay's existing line, rate stages
   and block allocator. Host tests first (the prototype's checks as pass/fail lines, plan section 7.3 item 17), an
   independent review, then the unit through the web installer's file option, after a backup.
4. Stage 2: the per-track instances (plan sections 4.1, 5, 6, 7), only after stage 1's numbers are in BUILD.md.

Nothing goes on the unit while the project-data-loss item is open (plan section 9, item 14).
