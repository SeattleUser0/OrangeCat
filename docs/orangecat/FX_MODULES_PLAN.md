# Orange Cat: effects as modules (Release 3, design only)

**Version:** 0.3 (October 31, 2026: section 12 answers Session C's MODULE_FORMAT_R3.md section 11; before that 0.2, October 29, after the independent review: twelve faults, all folded in below; written in Session A, round 7; design only, no code, read by the owner before any code)
**Branch:** release-2 (a document; nothing in the firmware changes)
**Depends on:** the project format revision (written separately, not yet handed over; the places that wait for it are marked **[format]**), the module loader of Release 1 (oc_module.c, fw_api.h, .ocm format 2), DUB TAPE as it ships in Release 2.
**Read with:** BUILD.md "DUB TAPE closed" (7.17), docs/orangecat/ENGINE_LOADING_PLAN.md (the engine modules), docs/orangecat/UI_BUILD.md on branch ui-build (Session C; read, not edited).

## 1. What this is for, and the scope

Engines can be modules today: SHAPES, WHEEL and the Prophet are installed from the installer page, the web app, the editor or the card, listed in the Engines table, admitted by cost. Effects cannot: DIST, DUB TAPE, the three buses and the reverb modes, the SLICER and the FX layer are all in the firmware image. Two reasons to change that. Flash is tight (UI_BUILD.md measures 40,000 B free on release-2, 24,416 B after its steps 1 to 3), and a player should be able to add an effect without a firmware update, as they add an engine.

**Scope, sized to the music.** Not a plugin SDK. Three kinds of effect, one loader, one host, no scripting, no per-sample callbacks into the firmware. Nothing here is built before the format revision is in hand. Each step below ships only when the step before it holds on the unit.

**What stays in the image for good** (a module costs a 4 KB sector at least, a header and a registry entry; below about 1 KB or on the voice path it does not pay): DIST (1.5 KB, on every track's voice path, six models), CHORUS (0.3 KB), AUTO PAN (0.3 KB), ROOM (the default reverb and the one every project has), the DELAY's core and its sized memory (DUB TAPE and the buses use its blocks), the master chain DJ FILTER, CLIP and LEVELER (1.8 KB, in the master path), and the host described below. These keep their place in the Effects table as **resident** entries, with module ids, so a project can name them the same way (section 3).

## 2. The module header: a kind field

Today's header is 60 bytes (`fw_mod_hdr_t`, fw_api.h): magic, iface, api_size, api_version, api_addr, engine, state_size, engine_ptr, link_addr, pack_hash, cost, version, length, crc, hcrc. Code starts at 0x100.

**The change.** The `engine` word keeps its low 8 bits as today (the engine number for kind 0). Bits 8 to 15 become **kind**: 0 engine (every module on a unit today: the word is unchanged), 1 insert effect, 2 send effect (a mode of a shared bus), 3 master effect. Bits 16 to 31 are 0. The header's size, CRC rule and sector-tail rule do not change.

**What refuses an effect module on an older unit: the interface identifier, not the kind.** Release 3 grows `fw_api_t`, so `FW_API_IFACE` changes once. Every older firmware then refuses an effect module on that check first: `fw_module_check` gives BAD_IFACE (boot: MD_REFUSED), the web page's `ocmCheck` and the card installer ("Not for this firmware") refuse before anything is erased. The same change refuses every engine module built before Release 3 on the new firmware, so **all modules are rebuilt for Release 3** (as in 0.12.1 and 0.14.0). The kind bits are not the guard: they are what the new loader reads. If the identifier did not change, an old firmware would read a word above 127 as an engine number, so the identifier must change in the same release as the first effect module, and a test on the old loader (host, tests/oc_module_test.c with the old table) shows the refusal.

**The install path is keyed on the engine number and must learn a module id.** This is the largest hidden work item and it comes first (section 11). The engine number is the key in `oc_mod_begin`, `oc_mod_plan`, `oc_mod_geo_of`, `oc_mod_remove`, the `oc_mod.engine[]` table (a byte), `eng_module_slot`, the editor's install commands (the engine goes as one 7-bit byte: commands 120 to 124), the card installer (card_install.c reads it from the .ocm) and the web page (`moduleCurrent`, `modInfo(ocm.engine)` in fm1oc.js). An effect has no engine number. Release 3 gives the install commands a module-id form (a new command pair or a flagged argument, decided with the editor protocol), the loader a table keyed by module id beside the engine-keyed one, and the card and the page the same. Engine installs stay on the old keys.

**Where a module can sit is fixed today, not "any free start".** `oc_module.c` allows 3 starts only (sectors 0, 6 and 4 of the 12 in the area) and a geometry row per engine: SHAPES 6 sectors at starts 0 and 6, the Prophet 8 at 0 and 4, WHEEL **4** at 0 and 6. At most two modules stand in the area now (SHAPES + WHEEL, or the Prophet + WHEEL); sectors 10 and 11 have no start. An effect module needs a **start grid** (a start at every sector boundary, spans checked for overlap by the planner instead of a fixed table), which is step 0 in section 11. The relocatable .ocm (format 2) already lets one image go to any start; the planner and the geometry table are what restrict it.

**What `engine_ptr` points at for an effect.** An `fx_desc_t` inside the module's image, read in place and checked pointer by pointer against the image before registration, as `fw_pages_check` does for an engine's pages. It holds: the module id, the module version, the capability fields (section 4), the parameter table (section 3), the pages. **Open:** `fw_pages_t` rows address a track's native block under SC_MOD with page indices reserved per engine (MODPAGE_ENG); DUB's own pages are track `p[]` ids under SC_TRACK (params.c) with ids hard-coded in ui_pages.c, and the "DUB FULL" flags are read by those ids. Whether an effect's pages reuse the engine row format or get a page kind of their own is decided in step 0 with the page-index slots (an effect has none today); this plan does not assume either, the kernel's entry points, an optional scene for the new interface (section 9). The loader's new work: for kind 1 to 3, validate `fx_desc_t` and register into the Effects table instead of the engine table. An effect module is an .ocm of format 2, linked at 0 with a relocation list; where it may be placed and how it is installed is the work above.

**One image, several effects.** A sector is 4 KB and the small reverb modes are 0.4 to 0.7 KB each. A module may carry up to eight effect descriptors (a **bank**: `fx_desc_t` is the first of a table of `n`, `n` in the descriptor's first word). One module id, one version, one install; each effect inside has its own effect id. This is how SPRING, SHIMMER and RESO share one sector.

## 3. Stable identity: (module id, version, parameter id)

Engines are identified by their slot number, which the firmware assigns (ENGI_*) and which a project stores. That is fine for a fixed list and wrong for a list that grows. Effects are identified by an id that belongs to the module and never changes.

- **Module id:** 32 bits, the first thing in `fx_desc_t`. Orange Cat's own: 0x0000_0001 and up, listed in a new file docs/orangecat/MODULE_IDS.md (DUB TAPE 1, then the resident effects as they get ids). Everyone else: bit 31 set, 31 random bits the author picks and the installer page checks against the ones it knows. The slot the Effects table gives a module is a run-time index and is never stored.
- **Effect id** inside a bank: 8 bits, stable.
- **Version:** 0x00MMmmpp as engines have it. The rule the loader and the project use: a minor or patch change never changes the meaning of an id or its range; a major change may, and a project that names an older major than is installed is loaded with that effect held **dormant** (below), not guessed.
- **Parameter id:** 16 bits, stable for the life of the module. Ids are never reused and never change meaning. A new parameter is a new id, appended. A removed one stays reserved in the table (`label` 0, as the engine panels do). The table gives each id its range, default and format (`param_desc_t`: label, format, min, max, default, names, unit) so the editor, the pages, the macros and motion read one description.
- **Resident effects use the same ids.** The firmware's own effect entries (DIST, DUB TAPE until it moves, the reverb modes, and so on) are registered at boot with a module id, a version and a parameter table, flagged resident. A project that names (module id, parameter id) loads the same whether the effect is resident or in a module. That is what lets an effect move out of the image (sections 6 and 7) without touching a saved project.
- **Legacy ids for DUB TAPE.** Release 2 stores DUB's values in fixed track parameter slots (P_RESERVED45..47 for LEN, PTRN, SPRP; P_JRES0..6 for FDBK, SEND, TONE, SPACE, THRW, CUT, KICK). The DUB module's parameter table carries a **legacy slot** for each id (`legacy` field, 0xFFFF for none); the loader of a project in today's format reads the slot and the writer of the new format writes the id. A project saved by Release 2 loads in Release 3 with DUB as it was.
- **A missing module.** A project that names a module id the unit does not have keeps that effect's record **dormant**: stored as read, shown in the track's effect page as "NAME NOT INSTALLED" with the module id, written back byte for byte on save, bypassed (the track plays dry) while absent. Installing the module wakes it with its saved values. **[format]** the project format revision must say where such a record lives and that unknown records are preserved on save; this plan assumes it does.

**What waits for the format revision [format].** Where an effect slot's record is stored (the module id, version and the values as id and value pairs, or as a block in the module's id order); how many effect slots a track has; how a dormant record is kept; how the macros' baked values (Session C's P_RESERVED33..36, section 9) and the legacy DUB slots coexist; whether motion can name an effect parameter. Until the revision is handed over, the host (section 5) is written against an abstract **effect parameter store**: `fx_get(track, slot, param_id)` and `fx_set(...)`, which the first implementation backs with the legacy slots for DUB and the new format backs later. Nothing else in this plan depends on how it is stored.

## 4. Capability fields

In `fx_desc_t`, per effect. The firmware reads these to decide admission, memory, scheduling and what the UI shows; the module does not enforce any of them.

| Field | Meaning | DUB TAPE (LITE) | CLOUD |
|---|---|---|---|
| `ram_state` | bytes of arena state per instance (the module has no .data or .bss: the build already checks this) | 2,864 (`dd_t`) | to measure (the CLOUD grain state) |
| `ram_work_min`, `ram_work_max` | work memory in 4 KB blocks (JFX_SEG, the shared DELAY's block table): the least that lets it run, the most it uses; the firmware gives between them by the effect's own setting | 2 to 16 (LEN 8K to 64K) | 8 (the 32 KB model line today) |
| `ram_extra` | blocks held only while an option is on (DUB's spring: 5,632 B) | 2 (spring) | 0 |
| `latency` | samples at 44.1 kHz the wet arrives after the input, constant; the firmware aligns a send's dry and reports it | 32 (one block) + the converters' 29 at the half rate | to measure |
| `tail` | how long the effect keeps sounding after the input stops: `tail_base` (blocks), a flag that the instance's own longest delay time is added (DUB: the farthest head's time plus 24 blocks, `hold_len`, refreshed while the input peak is above 132, -72 dB), and a flag "until silent" (the firmware keeps the track mixed while the peak is above that threshold, as `dub_alive` does) | flag: farthest head + 24 blocks | until silent |
| `rates` | the line rates it supports as a mask (44.1, 22.05, 11.025 kHz) and whether it changes them by itself | 22.05 and 11.025, automatic fallback | 5.5125 kHz |
| `seed` | whether it uses randomness: 0 none; 1 it takes the seed the firmware gives it | 0 (the LITE kernel has no wow) | 1 |
| `cost` | measured CPU1 time a block per instance at the worst setting, in microseconds, and the profile id class (same units as engines' measured cost: from the trace, not estimated) | 95 to 190 | to measure |
| `max_inst` | instances the firmware may run at once (the arena-handle count) | 4 | 1 (a bus) |
| `kind` | in the header (section 2) | insert | send |

**Deterministic seed.** An effect that uses randomness must give the same output for the same input and seed on the host and on the unit. The firmware passes a 32-bit seed in the instance's context at every (re)start: `hash(project seed, track, slot, module id)`, where the project seed is a stored value (**[format]**: one 32-bit field; until then a fixed constant, so a render is reproducible but two projects share it). The kernel must not read a global random state, a timer or the audio clock. A module with `seed` 0 may not read the seed. The host test of every effect module renders it twice from the same seed and compares the hashes (section 8).

## 5. The host in the firmware: one insert chain, one governor, one memory rule

The work Release 3 does is mostly here, not in the modules. DUB TAPE's integration today (jfx_dub.c, 363 lines, included by mix.c) is the model, and it is not generic: it knows its own states, memory handles, rate stage and governor. The first step (section 6) is to cut it into a **generic insert host** and the **kernel with its parameter table**, with DUB's kernel (dubdelay.c, already separate) the first thing on the far side of the cut.

**The insert chain.** Today a track's signal is engine, DIST, mute and solo, LEVEL, then (with DUB on) the capture point before PAN. Release 3 names this: a track has an ordered insert chain of **slots**. Slot 0 is the position after DIST (resident today: DIST stays a fixed stage, section 1); slot 1 is the position DUB has (after LEVEL, before PAN, the mono capture); a module effect of kind 1 takes slot 1 (and later slot 2, **[format]** decides how many slots are stored; the first implementation has the one DUB has, which is the one that is measured). The host does what `mix_send` and `dub_add_wet` do now for any kernel in the slot: capture the track's mono x, hand the previous block's capture to the kernel as a CPU1 job (the first descriptor of the voice batch, the shape measured in rounds 4 to 6), add the wet into the track's dry destination and, mono, through the track's own sends. Parallel to this, kind 2 (a mode of a shared bus) replaces the dispatch in `rev_run`: the reverb's mode number becomes an index into the Effects table, and the resident ROOM stays as index 0 so a unit with no module has the reverb it has. Kind 3 (a master buffer effect) takes the FX layer's place in the master chain (section 7).

**The kernel call.** `kernel(ctx, in, out, n)` where `ctx` is the host's instance context: state pointer, the work blocks' table (the 4 KB block pointers, as DUB's `dd_t` holds), the parameter copy for this block (a snapshot the host takes in `mix_prepare_batch` before the tracks render, after the macros are applied, as DUB's `dub_start` does), the seed, the rate stage and the block length. The kernel never allocates, never calls the firmware except through `fw_api_t`, and runs in the one CPU1 job the host gives it. `fw_api_t` grows by what an effect uses and an engine does not. From DUB's code today: the block-table access; the limiter and saturator helpers and the converter stages (`hb_dec`, `hb_int`, the constant-tap functions); the tempo (`beat_samples`, used in DUB's SPACE map and in its parameter-copy hash); the kick edge counter; `audio_batch_push_cost` with a **profile id** (an effect module has none of its own: the host gives each module a class id from a small pool and the cost table gets a row per class); `memset`, `memcpy` and `clamp` (the build rejects an undefined symbol); the CPU1-retired degrade (`dub_cpu_wait`, 2 s) and the reset request (`jfx_reset_req`), which stay in the host and reach the kernel as flags in its context. The count is not estimated here: it is read off the kernel's undefined symbols when step 1 is cut, and the table's size is reported then.

**Memory.** An effect's state and work blocks come from the same arena, in the same order and under the same rules DUB's do now (`jfx_take`: the shared effects served before inserts, JFX_GROW, JFX_RETRY, JFX_YIELD; main bank, cache bank and the card's lent slots; all or none). An instance that cannot get its `ram_work_min` blocks plays dry and its page says `NAME FULL` (DUB FULL today); the memory is checked at admission by the arena test's rules, using `ram_state` and `ram_work_min` (the same arithmetic the Engines table uses for an engine's arena). The effect's own memory setting (LEN) chooses between `ram_work_min` and `ram_work_max`. A module has no memory of its own beyond the instance's state and blocks: no .data, no .bss, as the loader already requires. DUB's memory layer (`jfx_dub_mem`, `jfx_free_dub`, `jfx_dub_lend`, about 1.25 KB) is host code and becomes the generic effect memory layer; it stays in the image.

**Caps.** The voice caps (MODAL, the Prophet, FM6) are per engine and stay so, with one coupling the host keeps: `dub_running` is the third column of the caps' accounting (voice.c), so a running insert tightens them. A generic host exposes it as "insert instances running". Effects get an **instance cap** (`max_inst`, a hard limit) and a **budget**: the host sums `cost` over the instances running and refuses a new one past the effects' share of CPU1's block (the figure comes from the trace rounds: DUB's job was 95 to 190 us in a block with the voices; the share is set from that measurement, not a guess, and written in BUILD.md when the host is built). **Units:** an engine's `cost` is instructions a sample from tests/target_budget.txt (fw_api.h). An effect's `cost` is a CPU1 time a block in microseconds from the per-job profile, and the header says which with a unit bit; the two are never summed together. This replaces "DUB admitted until the governor releases it" with the same admission an engine has at assignment (`eng_admit`): the Effects table shows an effect as available or NO ROOM, and says why.

**The governor.** DUB's late governor (`dub_late_half`, counting the time the DMA sees, round 4's accounting) becomes the host's, for every module effect: when the late score trips the host releases one running instance (ramp out over 3 ms, never a click, the memory given back), holds it off with the doubling wait DUB has (8, 16, 32 s), and lets it come back by itself when the load drops. As the code is today (jfx_dub.c, audio.c): the trigger is a late half, or one within 100 us of the deadline, accumulated to a score of 480 (about two late halves in a second), and the instance given way is **the highest running track index**, not the costliest. Release 3 keeps that rule (it is predictable; a cost-ordered rule is a later change and would need its own measurement). The owner's reading of DUB's limit (one DUB track holds in a lighter mix; in a heavy mix it backs off and shows DUB FULL, and the moment it backs off can cost one or two late halves) is therefore the reading for every module effect, and the plan does not promise better. A module cannot opt out of the governor and cannot read the clock to defend itself.

**Flash writes and the PC guard.** Unchanged. A module effect's code runs only inside the CPU1 job the host gave it and joined in the same block (the Release 1 argument: no effect code runs while flash is written). The PC guard's window already covers the module area while one is registered.

**The module area is the binding limit, not the image.** 12 sectors, with the geometry above: SHAPES 6, the Prophet 8, WHEEL 4. DUB TAPE as a module is about 8.5 KB of code and tables, so **3 sectors**; a bank of the small reverb modes 1; the FX layer's buffer effects 2. Today's 12 sectors hold SHAPES + WHEEL (10), or the Prophet + WHEEL (12), and nothing else: **no effect module fits beside the existing pairs**. With the start grid of step 0, a unit can hold SHAPES (6) + DUB (3) + the reverb bank (1) + 2 free, or WHEEL (4) + DUB (3) + the reverb bank (1) + the FX layer (2) + 2 free; the Prophet (8) + DUB (3) leaves 1. So moving effects into modules frees image flash and spends module sectors, and a player who installs the Prophet gives up most of the rest. The installer page states a sector count next to every module, and the update set decides what it installs (below). Growing the module area means moving the data-flash map, a separate decision that this plan does not make.

**Where module code runs from, and what it costs.** A module executes from the flash's plaintext XIP window, and the tables it reads per sample cost about 250 ns more a read there than from the image or RAM (core.h, engine_t.hot). Engines solved that with a hot set copied into the arena at registration; effect modules do the same (`fx_desc_t` gets the same `hot` list: DUB's tables, the half-band taps, CLOUD's windows). DUB's kernel in SRAM measured no gain (round 4), so the code's own placement is not expected to matter; the gate in section 6 measures it.

## 6. What moving effects frees in the image

Measured from the symbol table of the Release 2 build (release-2 876955a, the stats image, `nm -S` over the effect functions; static helpers inlined into other functions are counted with those, so these are lower bounds; the constant tables the symbols do not show are not counted either, and the numbers are redone from the link map when a step is built):

| Effect | Moves out of the image (B) | Step | Notes |
|---|---|---|---|
| DUB TAPE: the kernel (`dk_*` 2,306, `dd_*` 4,700, `ddm_exp` 158, `hb_*` 284) and its tables | about 8,500 | 1 | about 3 sectors. **Stays:** the host (`dub_start` 2,414, `dub_add_wet`, `dub_run`, `dub_reset`, `dub_late_half`) and the memory layer (`jfx_dub_mem`, `jfx_free_dub`, `jfx_dub_lend`, about 1,250 B): about 4,100 B that become the generic host |
| RESO, SHIMMER, SPRING (+ spring side) | 1,800 | 2 | one bank, 1 sector |

| SLICER (`sl_*`, `slicer_*`) | 2,174 | not planned | routes tracks and the returns; many hooks in mix.c |
| CLOUD (`rev_cloud`) | 1,252 | last | with its 32 KB model line; 1 sector |
| Stay for good: DIST 1,522, CHORUS 286, AUTO PAN 340, ROOM 1,234, DELAY 3,405, the master chain 1,758, the bus core | 8,500 plus the bus core | never | the bus core (`fx_*`, `jfx_bus_*`, `jfx_mem`) was not reproduced to the byte (3,883 against 5,154 by prefix, which includes 768 B of buffers); it stays whatever its size |

(The first draft of this table counted `dub_start` and the other host functions as moving, missed the kernel's `dk_*`, and counted the key hooks as moving. Prefix sums over a symbol table are approximate: static inline helpers fold into callers, and `bss` and data objects share some prefixes by up to a few hundred bytes.)

The movable total of the planned steps is about 15,500 B (DUB 8,500; the reverb modes with CLOUD 3,050; the FX layer about 4,000). **The plan's own cost is taken off that:** the registry, the module-id install path, the loader's kind handling and the host glue are estimated at 2 to 4 KB (measured on step 0 and 1; the first estimate of 1.5 to 2.5 KB did not count the module-id path), the `fw_api_t` growth a few hundred bytes. So the realistic gain of steps 1 to 3 and CLOUD is **about 11 to 14 KB of the 40,000 B free**, of which DUB is 5 to 7 KB on its own. And **during the release in which the resident copy stays beside the module the image is larger by the glue, not smaller**; the gain comes in the release that removes the resident copy. That is real, and it is not a rescue: Session C's nine interface steps (1 to 9, with 7a to 7c) are estimated against the same 40,000 B (24,416 B left after steps 1 to 3 as measured; its own final estimate is about 10,700 B). Release 3 does not count a byte it has not measured against Session C's gate (section 9).

## 7. The order of the effects, DUB first, CLOUD last

Each step is one module, built, suite-tested and then run on the unit against the resident version it replaces. The gate for every step: **the module's render is bit-identical to the resident effect's on the host (the hashes pinned in tests/jfx_dub_test.c and tests/dub_insert_test.c for DUB; golden renders added for each later effect first, as tests/golden.txt has no DUB row), the effect's CPU1 time a block per job (the trace's per-job profile, which resolves a few microseconds; the wall rows do not) is no more than the resident's plus the measured noise, and a project saved before the step loads after it with the same values.** The Release 2 rows g2 and the limit rows are run as confirmation, not as the gate: g1 does not hold DUB on the shipped arena (rounds 3 to 5), so "reads the same" there is a failing row and proves nothing. The resident code is removed in the step after the module has passed, not in the same commit, so a failed step costs a revert and not an image.

1. **DUB TAPE (kind 1).** First because it is already in the shape of a kernel (its kernel, dubdelay.c, is a file of its own; the control path in jfx_dub.c is the work), it is the effect Release 2's measurements are all about (rounds 1 to 6: a bit-exact comparison is possible), and it forces the generic host (section 5): the insert slot, the memory rule, the governor, the legacy slots. If the host works for DUB it works for a kernel with fewer needs. Gate: the common gate above, the converter and spring tests of tests/jfx_dub_test.c on the module build, the unit's rows g2 and a, b, c as confirmation; **DUB must not run slower as a module** (the 250 ns window effect is read from the per-job profile; if the quarter-rate kernel is more than a few microseconds a call slower, the hot set is the fix). The resident copy stays one release behind it, and **the update set must carry the module**: a firmware update or a card set installs DUB's module with it (the installer page's set manifest already lists modules), so removing the resident copy never takes DUB away on an update.
2. **RESO, SHIMMER, SPRING (kind 2, one bank).** The first send-kind modules: the host's `rev_run` dispatch becomes an index into the Effects table, ROOM stays resident at index 0. Small and independent; they prove kind 2, the bank layout and the tank memory handoff before the large one. The reverb memory is the one bus tank (11.9 KB) plus a model line; a mode change releases and takes memory as it does today.
3. **The FX layer's buffer effects (kind 3).** The largest saving after DUB. Coupling to watch: the layer's keys are read in the audio interrupt (`perf_press` from the key scan), so the **key hooks stay resident** and call the effect through the host; the module owns the buffer processing only. Measured before it moves: the keys' latency to the first buffer sample, which must not change.
4. **SLICER: not planned.** It owns the routing of tracks and returns; a module would need a larger service surface than the others together. Listed so nobody wonders.
5. **CLOUD (kind 2, last).** The heaviest of the reverb modes (32 KB of model line, "on a full mix is tight" in Release 1's known limits), probably the one that needs a `seed` (its grain state is to be checked in the source before the field is fixed), and the one whose admission and governor behavior matter most. It goes last because by then the kind-2 path, the hot set copy, the instance budget and the seed rule have each been used by a smaller effect on the unit. CLOUD's gate adds the Release 1 table rows for CLOUD (heavy set, four tracks); the reverb steps (2 and 5) are gated on their own rows from the Release 1 table and the effects-on caps rows, not on DUB's. Each two-hour run states its failure mechanism first, as the test policy requires: only where the host's scheduling changed (step 1 and CLOUD), and the Release 2 qualification result stands for anything that did not.

AUTO PAN, CHORUS, DIST, DELAY, ROOM and the master chain do not move (section 1). If a later release wants one, the same procedure applies.

## 8. Installer page, the Effects table and how it is tested

- **The page.** The installer page lists what a set contains from the set manifest (`ocm` names). An effect module is one more entry; the manifest gains `kind` and `module_id` (a manifest field, not read from the file, and checked against the file's header after upload: the page already checks the engine number the same way). The page shows Engines and, beside it, **Effects**; both channels (Standard and Nightly) list their modules with kind and sectors. The installer page's single-install flow is unchanged (commands 120 to 124).
- **The Effects table.** A new editor command, the next free number after 129 (to be taken from web/EDITOR_PROTOCOL.md when built), returns for each registered effect: module id, effect id, version, kind, resident or module, source start and sector count, state (OK, NO ROOM, REFUSED, BANNED), instances running, and the capability fields that matter to the page (RAM, cost). The web app and the editor show it beside the Engines table; assignment of an effect to a track's slot is by this table, as an engine's is.
- **Banning.** The crash mark and the three-strike ban (oc_module.c) apply to an effect module as to an engine: the module's `inuse` bit is set when a track's slot runs its kernel. A banned effect plays dry and says so.
- **Tests, to the test policy.** Host: the loader's every refusal for the new header (kind, `fx_desc_t` pointers, the bank table, the id and range rules), the fuzzers extended to the descriptor, a module build of each effect against the resident build (bit-identical renders, both seeds), the host's admission, governor and memory rules over the dual-core simulation (the existing tests/dual_core_test.c fault paths), the legacy-slot load of a Release 2 project. Unit: each step's gate rows (section 7) as designed experiments written in BUILD.md before they run, a smoke test after every flash, and the two-hour runs only for the steps that change the host's scheduling (step 1 and CLOUD), under the policy's rule that an unchanged subsystem reuses the earlier result.

## 9. Where this touches Session C's work on branch ui-build

Read from UI_BUILD.md 0.6 and the branch's log (af07864); nothing there is edited. The two designs touch in these places, and each needs a decision before either merges.

1. **Parameter ids.** The knob macros take P_RESERVED33..36 (P_MAC0..3). DUB uses P_RESERVED45..47 and P_JRES0..6. The effect parameter store (section 3) must not give a module a slot in those ranges; the legacy slot field exists so DUB's stay where they are. The macros' **bake** at save (a saved target is `clamp(stored + delta)` with the macro written as 0) is a project-format question for effect parameters too: a macro that targets an effect parameter needs the id to be (module id, parameter id) and the bake to write the effect's record. **[format]**
2. **Knob tables and macro targets.** Session C's `knob_def_t` table is per built-in engine, in firmware/src/oc_knobs.c, with targets `{id, shape, depth}` where `id` is a track parameter id. For a module effect the knob table must come from the module (the `knob` field of `fw_pages_t` already lists HOME's four knobs for an engine's panel); a macro target names a parameter id in the module's own table, and the host resolves (module id, parameter id) to the slot at registration. Session C's rule for knob tables (targets read at render time, never latched at note-on) holds for effects too and is a rule of the insert host: the parameter copy is taken once a block, in `mix_prepare_batch`, after the macros' call.
3. **Pictures and scenes.** The asset pack's scene trailer is where engine and effect pictures live until they are modules (the owner's decision 5). An effect module carries its scene in its own image (the optional scene pointer in `fx_desc_t`, validated by Session C's `scene_ok` with its 1 KB bound before any draw); the trailer entry for that effect is then dropped from the pack. This is the answer to the open item "the pack's room for the effects' and DUB TAPE's scenes (step 7b, 7c)": **the scenes of the effects that become modules go in their modules** (DUB, the reverb bank, the FX layer's buffer effects). DIST, AUTO PAN, CHORUS, ROOM, DELAY and the master chain stay resident for good, so their scenes still need the pack: Session C measures about 1,300 B for the eight effect pages and DUB against 115 B of spare, so the pack's room question stays open for those, and this plan answers only the module part of it. Note that Session C puts `scene` and `kdef` in **fw_pages version 3** (step 7a) while this plan puts a scene pointer in `fx_desc_t`: both rewrite the same struct and `oc_mod_pages_check`, so one of the two designs carries the field and the other reads it. To be agreed before either merges.
4. **The pack hash.** A module is refused if its `pack_hash` is not the firmware's. Session C kept the trailer outside the hash for exactly this. Effect modules should read nothing from the pack at all (their tables are in the image, copied to the hot set), so they stay loadable across any pack revision. This is a rule for the effect module template.
5. **EDIT's sheets and the FX link.** The sheets read pages as data; whether an effect's pages fit them is the open question in section 2. Session C's FX link is `open_family(FAM_FX)`, a family and not a slot: an effect module's pages must appear under that family, in the order of the Effects table.
6. **The flash ledger.** Both designs spend and free the same 40,000 B. Release 3 reports its freed bytes only as measured (section 6) and does not draw on them for the interface. Session C's gate (8,192 B left plus the later steps' estimates) is read against the number the unit's image measures at the time, whichever branch is ahead.
7. **Session A's files.** UI_BUILD.md lists `jfx*` and `audio*` as files the UI branch does not touch. Release 3's host changes exactly those. The merge order is the owner's call; the plan's only requirement is that the knob macros' audio-interrupt hook (`oc_macro.c`, waiting for Session A's review and timing) is reviewed before the host is cut, because both sit in the same block and both add a call before `mix_prepare_batch`.

## 12. Answers to MODULE_FORMAT_R3.md section 11 (round 9, October 31, 2026; design only)

Read: Session C's `MODULE_FORMAT_R3.md` 0.2 (branch ui-build), against sections 2 to 4 and 9 above. Its layout words and mine agree where they overlap (the kind bits 8 to 15 of the `engine` word; a 32-bit module id and an 8-bit effect id in a bank of up to 8; the capability fields; the legacy slot of a parameter; the hot set and the cost with a unit bit). Answers to its seven decisions:

1. **Picture and knobs reached from `fw_pages_t`, not `fx_desc_t`: accepted.** It replaces the optional scene pointer in section 9 item 3 and in section 4's descriptor; one place for the picture, one checker. An `fx_entry_t` points at its own `fw_pages_t` (scope SC_FX), so every effect in a bank has its own picture and knobs. The scenes of the effects that become modules therefore live in their modules, as section 9 item 3 already said.
2. **Engines keep slot numbers, no module id for engines: accepted, final.** Effects are keyed by (module id, effect id) and engines by slot; the loader keeps two tables, as section 2 ("the install path") needs. The install path for effects (the module-id install commands and the start grid, section 11 step 0) stays independent of this format.
3. **Effect pages reuse `page_t` rows under a new scope SC_FX appended after SC_DXLANE: accepted; it settles the open question of section 2** (reuse the row format, no new page kind). The insert host reads an effect's values by panel index through `pid` into its own parameter store; the rows' `shown`/`active` callbacks stay 0 for an effect until the host has a signature that takes (slot, instance, id), which is a host change in step 1.
4. **A bad picture or knob table does not refuse a module: accepted** for the picture and for knob targets. A bad capability word or a bad `pages` block refuses, as section 4 says; the picture is not a reason to refuse a sound.
5. **A `pid` that does not resolve is dropped, never guessed: accepted for knob targets and macros.** It does not apply to a project's stored values: those are kept as dormant records (section 3) when their module or parameter is missing, so a project round trip never loses an effect's setting. The two rules are different on purpose (a knob can be redrawn; a saved value cannot be recovered).
6. **The `ext` word in `fw_pages_t` as a placeholder with a version rule (a later use is version 4): accepted.** The effect host does not need it: its capability words are in `fx_entry_t`. Nothing in this plan asks for a use of `ext` before Release 3 freezes.
7. **Effect modules carry `pack_hash` 0: accepted** (it is section 9 item 4 as a rule). The gates that change are the ones listed there: `oc_module.c`'s registration and install checks, `card_install.c`, the page's `ocmCheck`, and the update set, which carries the module (section 5 of the plan: DUB moves out of the image, so the update must bring it).

One thing for the owner and Session C to hold to: **`fw_api_t` growth for effects (their section 7 item 2) is mine to list when step 1 is cut**; section 5's list (read off the kernel's undefined symbols: `beat_samples`, `audio_batch_push_cost`'s profile class, `jfx_take` and the arena calls) is the starting point, and it lands in the same identifier move as `fw_pages_t` version 3. Their `legacy_module` word in `fx_entry_t` matches section 3's rule for DUB (a nonzero key says the entry stands for a Release 2 resident effect whose values sit in fixed slots, and `fw_pid_t.legacy` gives each slot); the project format revision reads both.
